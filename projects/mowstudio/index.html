MowStudio

Booking infrastructure for creative studios.

Role
Solo · end-to-end
Period
July 2026 — Sep 2026
Stack
Next.js 16 · React 19 · TypeScript · PostgreSQL · Prisma
Shape
Modular monolith on Vercel (region sin1)

Problem

Photo, podcast, and music studios need scheduling that survives real concurrency: rooms have working hours and blocked slots, services carry duration and buffer, guests book without accounts, and a 30% deposit has to be collected and reconciled.

The hard part isn't drawing a calendar — it's making it impossible for two people to book the same slot at the same moment, and making a third-party payment webhook safe to receive twice.

Solution & architecture

One Next.js App Router application. Server Components render pages; Server Actions and Route Handlers are the transport layer; feature-first layering (application → domain → infrastructure) keeps Prisma, Supabase Auth, SePay, Resend, and Sentry behind adapters. There is no separate gateway — Vercel ingress is the boundary, with /api/health and /api/ready deliberately separating process life from database life.

  • Concurrency is enforced at the database. Booking creation runs in a Prisma transaction holding a PostgreSQL advisory lock per room + local date; overlap checks include duration and buffer; unpaid holds expire.
  • Payments are idempotent by design. SePay webhooks are verified (HMAC-SHA256), normalized to provider-neutral events, and deduplicated by (provider, eventId); the 30% deposit is computed in integer VND with BigInt, VietQR rendered per booking.
  • Guests without accounts still get private bookings — the raw access token lives in an HTTP-only cookie, only its hash is stored, matched in constant time; logged-in users can claim past guest bookings by email.
  • Roles are guarded server-side. Supabase Auth handles email/password and Google OAuth; admin pages and actions re-check the role in server code, never in the UI.

My contribution

Solo and end-to-end: the data model (11 Prisma models), the availability algorithm (15-minute slots across working windows, blocked slots, duration and buffer), booking and payment lifecycles, guest claim flow, the admin surface (rooms, services, schedule, blocked slots, calendar, payments and refunds), notification templates with send-log idempotency, structured logging with recursive redaction, and the CI pipeline.

Trade-offs

  • Modular monolith, not microservices. One deployable keeps iteration fast; the price is no independent scaling per feature — acceptable at studio scale, revisited if a partner API appears.
  • No queue or background worker yet. Emails send inline after mutations; the documented upgrade path is a transactional outbox once volume demands it.
  • Refunds are an operations state, not a bank integration: REQUESTED → PROCESSING → REFUNDED is tracked and audited, payout happens offline.
  • AuditLog exists in the schema without a write path yet — flagged in the project's own review, not hidden.

Evidence

The repository carries 65 unit/component test files and 12 Playwright E2E specs (desktop + mobile Chromium). A documented verification run in August 2026 reported 203 tests passing and the Playwright suite at 46 passed / 4 skipped — numbers tied to that run, not to a file count.

CI runs quality, integration (PostgreSQL 18 service), critical E2E, and build jobs on every push; production migration is gated behind an explicit confirmation env and separated from app boot.
