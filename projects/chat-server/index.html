Chat Server Microservices

Real-time messaging as a distributed system — twelve services, one shared contract layer.

Role
Shared contracts · file service · audit pipeline · UI/UX
Period
Jan — Jun 2026
Stack
Java 17 · Spring Boot 3 · Spring Cloud Gateway · gRPC · RabbitMQ · MySQL · MinIO · Keycloak
Shape
12 microservices · 15 Maven modules · Swing desktop client

Problem

A Discord-inspired platform: community servers and channels, direct messages and friends, presence, file sharing, and per-server RBAC — built as a microservices system where each service owns its database and nothing may cross a database boundary.

The difficulty is coordination: twelve independently-owned schemas that still have to behave like one product, over both synchronous calls and asynchronous events, while authentication migrates underneath them.

Solution & architecture

Spring Cloud Gateway terminates the edge and authenticates in dual mode — Keycloak tokens (RS256 via JWKS) first, legacy HS256 tokens from auth-service as fallback — then forwards identity as X-User-Id. Internally, services communicate over gRPC with contracts in the shared grpc-contracts module; asynchronous events (presence, notifications, logs) flow through a RabbitMQ topic exchange; WebSocket chat sessions are owned by messaging-service. Each service keeps its own MySQL schema.

  • Contracts before services. The shared modules — DTOs, enums, exceptions, and the Protocol Buffers contracts with generated gRPC stubs — were built first, so twelve services could be built in parallel against one vocabulary.
  • File service: MinIO (S3-compatible) uploads with a 10 MB cap and automatic thumbnail generation for images.
  • Audit logging is event-driven: sensitive actions are published to the exchange and aggregated centrally into Loki/Promtail — services stay decoupled from the log store.
  • Observability is part of the deliverable: Prometheus, Grafana, Spring Boot Actuator with Micrometer tracing, deployed via Kubernetes (Kustomize) and Jenkins.

My contribution

Within the 4-member team I owned the shared foundation: the common-lib (DTOs, enums, exceptions, utilities), the grpc-contracts module (proto definitions and generated gRPC stubs every service imports), and the file service with MinIO storage and automatic thumbnails — plus the event-driven audit logging pipeline over RabbitMQ and Loki. I also contributed to the Swing desktop client UI/UX, including its 3-column layout and light/dark modes.

Trade-offs

  • Database-per-service buys isolation at the cost of joins. Every cross-domain read becomes a contract call — cleaner boundaries, more hops.
  • Dual-mode JWT makes the Keycloak migration gradual, but two verification paths run at the gateway until the legacy issuer is retired.
  • Swing kept the scope on the backend. The desktop client is functional (3-column layout, light/dark), not the showcase; the system is the story.
  • Uploads cap at 10 MB — predictable file-service behavior without implementing chunked transfers.

Evidence

Graded 9.5/10 Java, 9.5/10 Microservices, and 10/10 DevOps in the course evaluation. The architecture, the twelve-service list with ports and databases, and the dual-mode gateway design are documented in the project README.
